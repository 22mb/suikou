# 日本語文書の執筆・校正スキル

このスキルは、日本語の技術文書、規程、業務報告書、提案書などを執筆、または既存の文章を校正するときに適用する実践的ガイドラインです。論理的で明瞭、かつ文書の性格に応じた自然で締まった日本語を作成することを目的とします。

# 第1部 ルール

## 守るべき制約

- **根拠（依頼の内容、与えられた資料や事実、既存の文）に基づかない内容・数値・程度・条件・固有名詞を足さない。**
  - **許容される補足（文脈の明示）**: 文脈から指示対象が自明であり、言葉を補うことで意味の誤解を防げる場合は補ってよい。
    - 例: PRの説明文で「今回は扱わないこと」を「今回のPRでは扱わないこと」とする。
    - 例: 「CIが赤くても信用されない」を「CIの結果が信用されなくなる」とする。
  - **禁止される補足（無根拠な追加）**: 文脈に明記されていない理由・目的・評価・程度を推測で付け足してはならない。
    - 不可例: 「環境の整合性を保つため」「開発者の待ち時間がむしろ増えてしまいました」などの、文脈にない因果関係を勝手に補うこと。
    - 不可例: 「不要にする」という内容に対して勝手に「撲滅する」と強い程度で表現すること。
- **根拠が示している強さのとおりに書く。** 主張や約束の強さを勝手に変えない。（推測を断定にしない。「行う」を「原則行う」に弱めたり、義務を強めたりしない）
- **強調語（「非常に」「完全に」「一切」「大幅に」など）を安易に足さない。** 根拠に基づかない誇張表現を用いない。
- **表記（コロン、括弧、スペース、用語）は文書の中で統一する。** 定められた規則や文書内の表記ルールに揃える。

## 基本ルール

### ルール1: 条件・時の表現
日常会話的な「〜したら」「〜とき」「〜しても」の多用を避け、客観的な技術文書・規程では「〜の場合」「〜した際」「〜した場合でも」を用いて論理関係を明瞭にする。
- **悪い例**: 使うときは、設定を確認してください。
  - **修正形**: 使用する場合は、設定を確認してください。
- **悪い例**: 迷ったら、「いま使っている機器に最初から入っているもの」から始めてみてください。
  - **修正形**: 迷った場合は、「今使っている機器に最初から備わっているもの」から使ってみてください。
- **悪い例**: クリックしても、画面が遷移しない。
  - **修正形**: クリックした場合でも、画面が遷移しない。
> *理由: 条件分岐の境界が明瞭になり、文書としての品格が保たれるため。*  
> *境界: 初心者向けの導入ガイドや親しみやすいブログ記事、口頭指示を模した会話文では、「〜したら」「〜するとき」をそのまま用いてよい。*

### ルール2: 不要な読点の削除
句節ごとに機械的に読点を打つ癖を排し、主語の直後や短い修飾関係での不要な読点を省いてテンポよく読めるようにする。
- **悪い例**: 切り出したサービスも、原則として Ruby で実装する。
  - **修正形**: 切り出すサービスも原則として Ruby で実装する。
- **悪い例**: 動作確認の方法と、その結果
  - **修正形**: 動作確認の手順とその結果
- **悪い例**: 20 人のプランに、30 人
  - **修正形**: 20人のプランに30人
> *理由: 過剰な読点は文構造の把握を妨げ、読書リズムを分断するため。*  
> *境界: 読点を省くと修飾の係り先が複数に解釈できる場合や、長い主語節と述語を区切る場合には、誤読を防ぐために読点を残す。*

### ルール3: 語順の整理と倒置の解消
文末に前提条件や主題が付け足される倒置を排し、主題や条件を文頭に提示して語順を整える。ただし、文脈にない目的や理由を勝手に付け足してはならない。
- **悪い例**: 最新の料金ページで契約前に必ず確認してください。
  - **修正形**: 契約前には必ず各社の最新料金ページでご確認ください。
- **悪い例**: 今日、まず1日目の15分から始めてみませんか。
  - **修正形**: まずは今日、最初の15分から始めてみませんか。
> *理由: 読み手が前提条件を先に把握でき、文構造を理解する認知負荷を減らせるため。*  
> *境界: アクション喚起を最優先とする短いキャッチコピーや見出しでは、あえて動詞や行動を先頭に出してよい。*

### ルール4: 「同じ」の使い分け
同一・同等・類似などの異なる概念をすべて平易な「同じ」で済ませず、「同一」「同様」などの的確な語彙を使い分ける。
- **悪い例**: 同じリポジトリ・同じデプロイ単位
  - **修正形**: 同一リポジトリ・同一デプロイ単位
- **悪い例**: Zustand だけを採用すると、Redux の thunk と同じような手書きのコードがそのまま残ります。
  - **修正形**: Zustand単体を採用した場合、Reduxのthunkと同様の手書きコードがそのまま残ることになります。
- **悪い例**: 同じ手動操作を今後不要にするための改善案
  - **修正形**: 同様の手動操作を今後不要にするための改善策
> *理由: 「寸分違わぬ同一物（同一）」なのか「形式や傾向が似ている（同様）」のかを区別し、論理の曖昧さを排除するため。*  
> *境界: 日常会話や、厳密な区別が不要で平易さを優先する解説文では「同じ」のままでよい。*

### ルール5: 客観的な文章語への統一
会話調の語彙や曖昧な動詞を、客観的な文章語に改める。理由接続の「ので」は「ため」にする。文脈にない文や感情描写を付け足してはならない。
- **悪い例**: 本番に出たか？
  - **修正形**: 本番環境にリリースされたか？
- **悪い例**: 手段ですが、設定の段階でつまずき、使わないまま終わっていました。
  - **修正形**: 機能ですが、設定の途中でつまずき、利用に至らないケースが見られました。
- **悪い例**: 落ちるテストが何度も再実行されるので、失敗するジョブほど完了までに時間がかかります。
  - **修正形**: 失敗したテストが何度も再実行されるため、問題があるジョブほど完了までに時間がかかります。
> *理由: 客観的な事実伝達を担保し、文書の説得力と信頼性を高めるため。*  
> *境界: 読み手に親近感を持たせるコラムや、FAQの「質問文」そのものを再現する場合は、口語的な表現を残す。*

### ルール6: 主客・立場の明確化
誰の視点か分からない曖昧な文言を避け、対象や主語を補うか、客観的な状態・受動態で記述する。
- **悪い例**: // 利用側:ローディング、エラー、キャッシュ、再取得をライブラリが管理する
  - **修正形**: // 利用側：ローディング、エラー、キャッシュ、再取得はライブラリ側で自動制御される
- **悪い例**: 各ジョブは冪等に実装する必要がある。
  - **修正形**: 各ジョブの処理内容は冪等に実装されている必要がある。
- **悪い例**: 今回は扱わないこと
  - **修正形**: 今回のPRでは扱わないこと
> *理由: 発話者の立ち位置の揺らぎをなくし、仕様や責任の所在を明確にするため。*

### ルール7: 見出し・表・箇条書きの体言止め
一覧性・視認性が求められる箇所では、文末を名詞句（体言止め）に統一し、並列関係にある項目の構文レベルを揃える。
- **悪い例**: 1. 固定sleepで待っていた / 2. テスト同士がデータを共有していた / 3. 外部APIと実際に通信していた
  - **修正形**: 1. 固定sleepによる待機 / 2. テスト間でのデータ共有 / 3. 外部APIとの実通信
- **悪い例**: resource class を柔軟に選べる
  - **修正形**: リソースクラスを柔軟に選択可能
- **悪い例**: 通知・決済の変更を、本体のデプロイと独立してリリースできるか
  - **修正形**: 通知・決済の変更を本体と独立してリリースできた割合
> *理由: 並列要素の構文構造（パラレリズム）を揃えることで、視読性と情報把握速度を向上させるため。*  
> *境界: 箇条書きが手順を示すステップ列であり、「〜すること」「〜する」と動詞で指示を統一している場合は体言止めにする必要はない。*

### ルール8: 専門用語・慣用表現の活用
日常語で大雑把に描写せず、定着している技術用語や慣用句を用いて簡潔かつ正確に伝える。
- **悪い例**: テストを書く意欲が下がる。
  - **修正形**: テストを書く意欲が削がれる。
- **悪い例**: アラート条件
  - **修正形**: アラート発報条件
- **悪い例**: 読み飛ばされ
  - **修正形**: スキップされ
> *理由: 定着した用語・慣用句を用いることで、誤読を防ぎ、専門的な文脈を的確に伝達できるため。*  
> *境界: 非エンジニアや初学者向けの解説で、専門用語を使うと理解が難しくなる場合は、平易な日常語で噛み砕いた表現を選ぶ。*

### ルール9: 助詞と接続表現の整理
助詞「の」の3回以上の連続を漢字複合語で解消し、「で」「について」などの助詞を「における」「による」「を用いて」などの複合助詞に整える。
- **悪い例**: リースの期限を過ぎた
  - **修正形**: リース期限を過ぎた
- **悪い例**: フィーチャーフラグで、ジョブ種別ごとにエンキュー先を PostgreSQL に切り替える。
  - **修正形**: フィーチャーフラグを用いて、ジョブ種別単位でエンキュー先を PostgreSQL へ順次切り替える。
- **悪い例**: 次の対応も行いました。
  - **修正形**: 以下の対応も実施しました。
> *理由: 係り受けの多義性を解消し、引き締まった文章にするため。*

### ルール10: 案内・依頼の敬語表現
マニュアルや案内文で読者に行動を促す際、直接的な命令や強い否定を避け、丁寧で品位ある表現にする。
- **悪い例**: 注意してください
  - **修正形**: ご注意ください
- **悪い例**: という形で、実質的に修正を求める書き方はしないでください
  - **修正形**: のように、実質的に修正を求めるような書き方は避けてください
- **悪い例**: ご意見やご懸念がございましたら
  - **修正形**: ご意見やご懸念点などをお聞かせいただけますでしょうか
> *理由: 相手への配慮を示しつつ、協調的で円滑なコミュニケーションを促すため。*

## 文脈による使い分け基準

以下の一連の組は、一律にどちらかへ倒すのではなく、文脈と目的に応じて書き分ける。

### 1. 語句を補う / 冗長な表現を省く
- **語句を補う**: 主語・目的語や「発報」「機能」などの限定語が欠けており、指示対象が曖昧なとき。（例: 「今回は扱わない」→「今回のPRでは扱わない」）
- **冗長な表現を省く**: 前後の文脈から自明な語句の重複や、不要な機能語が文を引き締める邪魔をしているとき。（例: 「チーム内で規約として周知する必要があります」→「チーム内での規約周知が不可欠です」）
- **両立の条件**: 「意味の解像度を上げるための必要最小限の語を補い、修辞的な重複や不要な言い回しを削る」。

### 2. 助詞「の」を省く / 補う
- **「の」を省く**: 「の」が連続して係り受けが曖昧なとき、または複合名詞（熟語）として確立しているとき。（例: 「リースの期限」→「リース期限」）
- **「の」を補う**: 名詞の連結によって語の区切りが不自然になり、読みづらいとき。（例: 「複数ファイル」→「複数のファイル」、「コードコメント」→「コードのコメント」）

### 3. 指示語を補う / 削る
- **指示語を補う**: 直前の文や段落との因果関係・参照関係を明確にするとき。（例: 「これにより、」「本施策では」）
- **指示語を削る**: 指示代名詞（「これ」「その」）が乱立し、何を指しているか不明瞭なとき、または名詞を直接指したほうが明快なとき。

### 4. 名詞化する / 動詞化する
- **名詞化する**: 見出し、表のセル、箇条書き、定義文で一覧性と視認性を高めたいとき。（例: 「APIを数える」→「API数の計測」）
- **動詞化する**: 処理の手順、時系列のアクション、ユーザーの具体的な振る舞いを明確に指示するとき。（例: 「〜の検討」→「〜を検討する」）

### 5. 鉤括弧でくくる / 引用をやめる
- **鉤括弧でくくる**: 画面上のボタン名、コマンド名、選択肢、特定の用語を地の文から際立たせるとき。（例: 「承認」「変更依頼」のいずれかを選択）
- **引用をやめる**: 間接疑問文や一般的な概念であり、鉤括弧をつけると会話調や誇張に見えてしまうとき。（例: 「どの粒度で分けるか」→「どの粒度で分割すべきか」）

### 6. 疑問形をやめる / 疑問形にする
- **疑問形をやめる**: 測定指標、設計方針、報告書の要点として客観的に記述するとき。（例: 「リリースできるか」→「リリースできた割合」）
- **疑問形にする**: トラブルシューティングのチェック項目、FAQの見出し、読者の関心を引く導入部。（例: 「設定に誤りはありませんか？」）

### 7. 表現を和らげる / 禁止を明確にする
- **表現を和らげる**: 読者向けのガイドライン、レビュー依頼、協調的な行動を促す案内。（例: 「〜しないでください」→「〜は避けてください」）
- **禁止を明確にする**: セキュリティ規程、法務・コンプライアンス規則、重大な障害につながる操作。（例: 「本番データベースの直接操作は禁止します」）

### 8. 時制を過去形に揃える / 現在形にする
- **過去形に揃える**: 障害報告書、事後レビュー、過去の実験結果の記述で、当時の事実関係を客観的に報告するとき。（例: 「〜が原因でした」「〜という危険な状態でした」）
- **現在形にする**: システムの恒久的な仕様、アーキテクチャの解説、一般的な動作原理を述べるとき。（例: 「本機能はキャッシュを返却する」）

### 9. 敬体に揃える / 常体に揃える
- **敬体（です・ます）に揃える**: 顧客向け提案書、利用ガイド、社内報、一般的な依頼文。
- **常体（だ・である）に揃える**: 技術仕様書、システム設計書、社内規程、学術的レポート。同一文書内での混在は不可。

### 10. 補足を括弧書きにする / 本文に組み込む
- **括弧書きにする**: 箇条書きや表の中で、補足条件、別名、単位などの主たる情報と区別したい付帯情報を添えるとき。（例: `Larger runners（最大64コア、Arm対応）`）
- **本文に組み込む**: その情報が因果関係や論理の骨格をなしており、括弧にすると文章の流れが寸断されるとき。

### 11. 中黒・記号を使う / 接続詞・助詞に改める
- **中黒（・）やスラッシュを使う**: 表のヘッダー、短い箇条書き、密接に関連する単語の並列で視認性を優先するとき。
- **接続詞・助詞（「および」「または」）を使う**: 規程や契約、厳密な仕様書で、論理的なAND/ORの境界を厳密に区別する必要があるとき。

### 12. 表記の漢字・かな選び
- **漢字にする**: 実質的な意味を持つ動詞や、改まった表現として引き締めたいとき。（例: 「特に」「構いません」「繋いで指定する」）
- **かなにする**: 形式名詞、補助動詞、常用漢字表外の語、または漢字にすると別の意味に見誤りやすいとき。（例: 「〜にとどめる」［「止める」だとstopに見えるため］）

### 13. 文の結合と分割
- **1文にまとめる**: ぶつ切りの短文が連続し、前後の因果関係や対比が分断されているとき。（例: 「テストを多数実行するため、失敗する確率は跳ね上がります」）
- **文を分ける**: 1文に複数の条件や論点が詰め込まれ、主述の呼応がねじれているとき。

### 14. 「とき」「場合」「際」の使い分け
- **「場合」**: 一般的な仮定条件や状況設定（広く用いる基本語）。
- **「際」**: 特定の時点、機会、アクションのタイミングを指すとき。同一文脈での「場合」の重複を避けるときにも用いる。
- **「とき」**: 会話調の文面や、平易さを最優先する読者向け案内。

### 15. 能動態と受動態の選択
- **能動態**: 人間（開発者、運用者、ユーザー）が主体的に行うアクションや指示を前面に出すとき。
- **受動態**: システムの内部挙動、設定に基づく自動処理、客観的な状態変化を描写するとき。（例: 「ライブラリ側で自動制御される」）

# 第2部 手順

## 執筆の手順

1. **文体と表記の事前決定**: 書き始める前に、文書の目的（技術仕様書、社内規程、業務報告など）に応じた文体（[敬体に揃える / 常体に揃える]）、表記規則（コロン、括弧、英数字スペース）、および主要な用語を定義する。
2. **骨子の作成とドラフト作成**: [ルール3: 語順の整理と倒置の解消] に従い、主題や前提条件を文頭に置き、論理的な順序で文章を組み立てる。[守るべき制約] に反する不要な誇張表現は入れない。

## 校正の手順

1回の通読で全種類の問題を同時に探すと見落としが急増するため、校正は必ず以下の段階を踏んで実施する。

1. **文書の全体把握**: 全体を通読し、文書の種類、文体（敬体・常体）、既存の表記ルール（括弧、コロン、スペース、専門用語の統一状況）を把握する。
2. **群ごとの走査（複数巡の走査）**: 第1部のルールの群ごとに、文書の先頭から最後まで走査する。1回の走査では1つの群だけを対象とする。
